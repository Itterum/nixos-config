# Niri desktop restoration design

## Goal

Restore this repository as a reproducible configuration for a future physical NixOS workstation. The system will use Niri as its compositor and will remain usable before Itterum Shell is ready for Niri. The current Omarchy machine is only a development and validation host; applying this NixOS configuration to it is out of scope.

The same work also repairs the official multi-user Nix installation on the current Omarchy host so repository evaluation and builds can run reliably.

## Starting point

Commit `697e781` is the last complete desktop configuration before the repository was replaced by the WSL-only layout. It contains useful modular NixOS and Home Manager composition, Niri configuration, desktop services, applications, and evaluation tests. It also contains machine-specific and obsolete choices that must not be restored unchanged:

- NVIDIA RTX 5060 configuration;
- Limine, Secure Boot enrollment, and a Windows boot entry;
- fixed monitor names and output settings;
- Noctalia and Noctalia Greeter;
- assumptions that the generated hardware configuration belongs to one existing machine.

The current `itterum-shell` submodule is retained. It exposes only a development shell and still contains direct Omarchy and Hyprland dependencies, so this phase does not install or start it as the desktop shell.

## Restoration strategy

Restore selected files from `697e781` as normal working-tree changes on top of the current `main` branch. Do not reset or rewrite Git history. Reuse the earlier module boundaries where they remain appropriate, then adapt their composition for a portable Niri desktop.

The repository will use these layers:

- `hosts/desktop/` selects the future physical host and its replaceable hardware file;
- `profiles/nixos/workstation.nix` composes reusable system modules;
- `profiles/home/workstation.nix` composes the user environment;
- `modules/nixos/` owns system services and the Niri session;
- `modules/home/` owns compositor settings, fallback desktop components, applications, editor, and shell tools;
- `home/itterum/` is the Home Manager entry point;
- `tests/configuration.sh` evaluates portable invariants.

The old top-level `configuration.nix`, `home.nix`, and `helix.nix` WSL-era layout will be removed after their still-relevant settings have been incorporated into the restored modules.

## Flake composition

The flake will expose one configuration, `nixosConfigurations.desktop`, for `x86_64-linux`. It will pin matching Nixpkgs and Home Manager releases and retain the Niri flake used by the previous working desktop configuration.

The `itterum-shell` submodule remains a local flake input so its source relationship is explicit. No NixOS or Home Manager module will claim to enable the shell until that flake exports an installable package or module and its Hyprland-specific runtime dependencies have been replaced.

Home Manager will be integrated as a NixOS module for the `itterum` account. Shared arguments will pass flake inputs to both NixOS and Home Manager modules.

## Portable host and boot boundary

The repository cannot know the storage, CPU, GPU, or firmware of the future computer. `hosts/desktop/hardware-configuration.nix` will therefore be a tracked bootstrap placeholder with an intentionally invalid root filesystem label. The README will require replacing it with the file generated by `nixos-generate-config` before installation.

The portable host will not enable NVIDIA, AMD, or Intel GPU-specific settings. Hardware-specific modules can be added to the host imports after the target machine is known.

The bootstrap boot policy will target ordinary UEFI hardware with systemd-boot and a mounted EFI system partition at `/boot`. Secure Boot enrollment, dual-boot entries, disk identifiers, and vendor-specific kernel settings remain out of scope. A future host can replace the boot module without changing the reusable workstation profile.

`system.stateVersion` and `home.stateVersion` will remain `26.05`, because this is intended for a fresh NixOS 26.05 installation rather than an already activated older NixOS system.

## Desktop runtime

The system layer will enable:

- Niri as the Wayland compositor;
- greetd with tuigreet as a small independent login path;
- PipeWire and WirePlumber for audio;
- NetworkManager and a network tray integration;
- Bluetooth;
- XDG desktop portals suitable for Niri and GTK applications;
- polkit and GNOME Keyring support;
- udisks2, gvfs, and upower for desktop device integration.

Home Manager will provide temporary independent desktop components so the session remains operable without Itterum Shell:

- Fuzzel for application launching;
- Mako for notifications;
- swaybg for wallpaper;
- swaylock for locking;
- swayidle for lock and display-idle behavior;
- Waybar for workspaces, clock, network, audio, and the status tray.

Niri key bindings will invoke these standard components. They will be isolated in focused modules so Itterum Shell can replace them incrementally instead of requiring another repository-wide rewrite.

Machine-specific output blocks from the old configuration will not be restored. Niri will use automatic output discovery until a real host adds its own output module.

## User environment

The restored Home Manager profile will keep the useful command-line and development environment from both the previous desktop configuration and the current WSL-oriented files:

- Zsh, Starship, direnv with nix-direnv, Git, GitHub CLI, fzf, zoxide, eza, bat, btop, and tmux;
- Helix and its existing language servers and formatters;
- core development tools such as ripgrep, fd, jq, tree, uv, kubectl, k9s, and Codex;
- Ghostty, Nautilus, Firefox, KeePassXC, Telegram Desktop, and Obsidian as the initial graphical workstation set.

Google Chrome, Brave, the ChatGPT desktop package, Kooha, Gradia, and other historical extras will not be restored in this phase. They can be added later without changing the desktop architecture.

## Itterum Shell boundary

This phase prepares, but does not implement, the shell migration. The contract for the next phase is:

1. `itterum-shell` exports a Nix package and preferably a Home Manager module.
2. Its runtime command and environment use Itterum names rather than requiring `OMARCHY_PATH`.
3. Hyprland-specific imports and commands are replaced by compositor adapters, including a Niri adapter.
4. A systemd user service starts one long-running Quickshell instance inside the graphical session.
5. Standard fallback components are disabled only as each equivalent shell capability becomes operational and tested.

This boundary avoids declaring a successful shell integration while the current source is still tied to Omarchy and Hyprland.

## Repairing Nix on the current Omarchy host

The installed Nix 2.35.2 tree, build users, daemon unit files, shell initialization, and store are present. The system-level links that register `nix-daemon.service` and `nix-daemon.socket` with systemd are missing, leaving clients configured for the daemon store with no listener.

The repair will:

1. verify the unit and tmpfiles sources under the active default Nix profile;
2. register the supplied service and socket units with systemd;
3. create the supplied Nix tmpfiles configuration if it is missing;
4. reload systemd and enable socket activation immediately and at boot;
5. verify the socket, daemon activation, store access, and a real flake evaluation/build.

The existing Nix store will not be deleted or reinstalled. The repair is limited to the missing integration generated by the official multi-user installer. If privilege elevation cannot be completed through the desktop prompt, the exact reviewed commands will be handed to the user for execution in an interactive terminal.

## Validation

Repository validation will include:

- formatting and syntax checks for changed Nix files;
- evaluation tests for the flake output, hostname, account, state versions, Niri, greetd, audio, networking, portals, and fallback desktop services;
- negative assertions that WSL, Noctalia, machine-specific GPU configuration, fixed monitor names, and automatic Itterum Shell startup are absent;
- `nix flake check path:. --no-build`;
- a no-link build of `nixosConfigurations.desktop.config.system.build.toplevel`.

The hardware placeholder intentionally makes the result unsuitable for installation until replaced, but it must still allow evaluation and building on the current host.

Current-host Nix validation will include `systemctl` state, a successful daemon-store query, and successful execution of the repository checks. Before completion, Git status and diff will be reviewed to confirm there was no reset, commit, or unrelated modification.

## Recovery and safety

All repository restoration remains an uncommitted patch for user review. No force checkout, reset, commit, or push is part of this work.

The current-host daemon repair creates only systemd registrations and a tmpfiles link pointing at files already supplied by the installed Nix profile. These registrations can be disabled and removed without deleting the Nix store. No NixOS activation will be attempted on Omarchy.
